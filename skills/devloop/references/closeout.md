# devloop 收尾：提炼知识、保存证据、准备下一轮

用户说「收尾 / 归档 devloop」或 `next` 返回 `finalize` 时读取。本协议也用于旧流程，直接从当前执行区开始，不重新 grill 或重签历史文档。

## 1. 核对交付范围与证据

1. 找到活跃 worktree，读 plan、spec、当前与历史 attempt 的报告/acceptance。源 checkout 有冻结指针时跟到执行区，不把旧副本当当前状态。
2. 运行 `status --plan ...` 和 `next --dir ...`。每条 R 必须有已完成切片；逐片找到真实 reviewer 验收原件，核对 attempt/goal/base/head、结论、范围及门禁证据。全 done 仅是计划状态，缺证据不能宣布完成。
3. 独立 reviewer 的结论是本地交付依据。主会话核对报告，不能重新编写 acceptance 或替 reviewer 放行。冻结最后 reviewed HEAD；知识文档后续单独提交时，分别记录交付 head 与知识提交，不把代码验收结论移到新 HEAD。
4. 将遗留事项分类：原承诺未完成→留本轮修复/重开；证据缺失→未验证并指定验证路径；范围外的新价值→候选。BLOCKED、人工验证和真实路径未触发都照实保留。原承诺缺口未解决时只做阶段快照，不声称已收尾。
5. 不机械重跑昂贵或产生外部副作用的 E2E；按已授权的 reviewer 契约核验。需新增独立验收时委派 reviewer，避免为了收尾污染原现场。

## 2. 用一份 closeout 清单组织收尾

```bash
<skill>/scripts/devloop init --id <id> --root <执行区>/.devloop --stage closeout
```

从 `templates/closeout.md` 填写。这个文件留在被排除的控制面内，承接审阅材料、知识去向、未验证项、发布交接和候选；不是新的需求事实源，也不覆盖 plan 状态。

## 3. 按内容归位

按 [知识维护协议](knowledge.md) 核对 settle 后的持久规格，并把执行期间已确认的变更合并回同一能力文件：

| 内容 | 归位目标 |
|---|---|
| 需求、行为和验收契约 | `docs/knowledge/specs/<capability>/spec.md` |
| 跨能力领域概念和不变量 | `docs/knowledge/domain/` 或已有领域文档 |
| 经验、排障与操作方法 | `docs/knowledge/playbooks/` 或已有手册 |
| ADR、用户判断与取舍理由 | `docs/knowledge/decisions/` 或已有 ADR |

完整 R 映射、需求及验收场景必须保留，不能只提炼几个知识点后丢弃规格。同步规格/知识索引和替代关系；新增经验、ADR 可以为零。归位 diff 与已确认语义及验收事实一致、相关链接可读、closeout 逐项记录去向，才算归位完成。

执行材料留在本地任务目录：聊天逐字稿、逐 tick 记录、临时探查、重试日志、被替代草案、terminal handle。长期文档保留稳定任务 ID、实际确认来源、相关 commit 和必要证据摘要/持久链接；不能只指向被忽略或即将删除的文件。

知识回写只修改本项目文件，不自动写个人全局 memory 或外部知识库。范围沿用 plan/用户授权；如未约定目标文件，先生成具体知识 diff 再让用户审阅。收尾用户已授权提炼回写时直接执行常规文档更新，不额外索要一次许可。新的业务逻辑或程序测试仍按实现/验收流程处理，不混进协调者的文档收尾。

记录每条知识的目标路径、来源、处置（已写入/合并已有/不保留及原因）。不把未经验证的猜测转成规定。最后的知识 diff 自查与当前实现/生效决定一致；需要提交时遵循已有提交授权和路径 allowlist，仅暂存知识及业务产物，不暂存整个 `.devloop/`。

## 4. 发布交接与效果观察

复用项目既有发布机制，填写：待发布 commit/制品、验证证据、目标环境、发布命令或既有流水线、回滚命令、健康指标/基线/观察窗口、负责人和实际授权来源。

- 默认是「本地已验收，未发布」。没有发布授权时准备完整交接材料，等待相应授权；没有可核实的命令写明所缺条件，不虚构命令或发布结果。
- 用户已授权发布时，先核对要发布的提交与验收范围一致，再使用项目已有工具执行；沿用环境权限和发布门禁。发布成功记录真实版本、时间和链接，随后观察约定指标。
- 只有指标实测满足约定才记「效果已验证」。发布失败按已授权的回滚路径处理；超出授权时明确升级给用户。
- 这版不搭新发布平台、不常驻采集指标；可以在下一次会话带上发布结果/反馈再运行收尾分析，增量更新候选。

发布未获授权不妨碍本地交付归档；发布状态和原验收范围必须各自明确。不能用「本地完成」冒称「已上线」。

## 5. 下一轮候选与选择

只生成有依据的候选，优先展示最多 3 项，允许为零；更多项链接项目既有 backlog，不建第二套任务系统。

每项必须包含：候选 ID、观察/证据、受影响者与价值、目标、最小验证、依赖与优先理由、处置（待选择/已选/排期/拒绝及原因）。候选来源包括明确延期项、review/真实使用的发现、发布指标；冻结副本的非目标表必须与当前实现核对后使用。

本轮承诺缺口不进候选；未验证项单列，避免整体 PASS 抹掉未触发路径。已授权的修复照原计划继续，不能重新排成候选。拒绝项无新证据不重复提案。

用户选中候选后：新建不同的 devloop ID，intent 记录 `parent_devloop`、候选 ID、来源证据和相关生效知识；查当前代码与基线，只补问新增问题。已有低风险维护预授权时，可在允许类别/路径、轮次或预算、停止条件内自动继续；将匹配的授权来源写清，超界或无授权时仅提出候选。不得默认为无限新开循环。

## 6. 归位核对与过程清理

停止本轮 sentinel 与已结束 session，核对没有 impl/reviewer/compiler 正在写文件，释放已确认结束的阶段锁。保留尚需人工验证的业务现场。

核对 `docs/knowledge/specs/`、domain、playbooks、decisions 的本次产物与索引；逐项确认可进入 Git，暂存时明确列出这些文件和 `.devloop/.gitignore`。发布交接归入项目既有发布记录或 playbooks，需跨会话保留的下一轮候选进入既有 backlog；没有 backlog 时可在规格的后续事项中记录候选及处置。closeout 只保留本轮检查过程与去向。

原始过程材料默认留在 `.devloop/<id>/` 并被 `.devloop/.gitignore` 中的过程规则忽略，不再整包压缩到外部目录。归位不自动删除任务目录或 worktree。明确授权清理后，先确保长期产物已提交或已保存到仍保留的 checkout，必要确认来源、验收摘要及外部证据已持久保存，再清理；否则保留现场并说明缺口。已有压缩档案保留原状，不作为新的归档机制。

最终汇报给出规格/知识文件、逐类处置、提交状态、发布状态、未验证项及候选去向。归位完成与业务验收、发布完成分别报告。

## 旧流程兼容

- 仅收尾旧流程：使用其已确认 scope 与原始验收证据；新增 closeout 清单，不改历史签字或重写报告。`next` 的新严格检查失败要分清历史格式与真实遗漏，不能只改文字制造通过。
- 已跟踪 `.devloop/`：init 只提示，不执行 `git rm --cached` 或重写历史。仅对过程文件按明确路径停止跟踪，保留 specs 与忽略文件；索引变更单独审阅，不重写历史。
- 旧 plan 确认写了自然语言：保留原确认来源；继续执行确需规范化时，只根据实际授权填写规范结论，重新核对绑定、编译当前 goal。没有证据不补签。
- 本规程取代早期外部整包归档方案；旧任务使用现有原件提炼并归位，不需要重签原审批。
