# 项目知识：入口、读取与维护

新开、恢复、收尾和从候选启动下一轮时执行本协议。每次会话进入或切换执行 worktree 时检查一次；巡检 tick 不重复扫描。

## 1. 检查并初始化入口

先找到实际项目根目录；已有流程跟随冻结指针到执行 worktree。执行：

```bash
<skill>/scripts/devloop setup --project <项目根目录> --check
```

入口缺失时，由协调者运行同一命令去掉 `--check`，无需用户记忆命令或另开初始化流程。用户限定只读时只检查并报告缺口；路径冲突或权限失败按实际错误处理，不反复初始化。

`setup` 创建 `docs/knowledge/index.md`、`docs/knowledge/specs/index.md` 和 `.devloop/.gitignore`，向 `AGENTS.md` 追加入口；已有正文保留，缺少规格索引链接时补入，重复运行不重写。它只引用已存在的常用文档入口；其它文档由 Agent 根据项目事实补充。符号链接或文件/目录冲突不自动改写。

`setup --check` 退出 0 表示知识/规格索引和 AGENTS 入口存在、过程忽略规则就绪且 specs 可被 Git 看见，输出 `knowledge_status=initialized`；缺入口或规则不正确退出 1。`knowledge_content=unchecked` 表明**没有验证内容准确性、索引链接或知识完备性**。首次生成的索引仍需下节的内容核对，不新增“全项目知识整理通过”门禁。

`init` 先维护控制面内的 `.gitignore`，再对目标 Git worktree 根目录调用相同的只读知识检查；非 Git 时用 `--root` 的父目录。缺知识入口提示 setup，仍创建任务，不自动改知识内容。独立存放控制面时，由协调者对真实项目另外运行 setup。

旧版曾使用 `.devloop/specs/`。发现该目录时，协调者先将规格按能力归并到 `docs/knowledge/specs/`：目标不存在可移动，目标已存在则逐文件比较并合并，保留未受影响需求和证据；修正规格、知识索引及引用它们的项目文件中的相对链接。核对内容和链接后移除旧空目录，再运行 setup。CLI 遇到旧目录会明确提示，避免生成两套规格或自动覆盖冲突；它只自动替换知识索引中已知的旧入口链接。`.gitignore` 的旧 specs 例外随 setup/init 清除。

## 规格和领域知识的边界

| 产物 | 位置 | 权威内容 |
|---|---|---|
| 定稿 spec | `docs/knowledge/specs/<capability>/spec.md` | 该能力的需求、行为、接口契约、验收场景；实现状态单列 |
| domain | `docs/knowledge/domain/` | 跨能力共享的术语、实体含义、状态模型和业务不变量 |
| ADR / 决策 | `docs/knowledge/decisions/` | 为什么选择某方案、替代方案、适用边界、实际用户裁决来源 |
| 经验 | `docs/knowledge/playbooks/` | 可复用的排障/操作方法、根因与预防办法 |

例如：“工单完成后不可再绑定执行”若是跨能力共享不变量，定义在 domain；“绑定接口收到已完成工单时返回什么错误”定义在对应 spec 并引用该不变量。能力特有规则只写 spec，domain 不再复制整份需求。已有同职责领域/ADR/手册文件优先更新原文件，索引引用它。

## 定稿 spec 归位（settle）

1. spec 已消除本轮需求歧义、取得真实确认并通过正式门禁 B 后，协调者按能力创建或更新 `docs/knowledge/specs/<capability>/spec.md`，参考 `templates/specification.md`。联审模式在签署封存后执行；草稿和打回内容仍留在任务目录。
2. 读取已有能力规格，将本轮新增、修改、删除的需求合并进去，保留未受影响的需求及稳定 ID；更新同一能力文件，Git 保存历史。归位 diff 逐条映射本轮 R，避免后来同名 R 覆盖旧能力要求。只归位已确认语义，冲突或新增要求回原审阅流程。
3. 持久规格保留完整需求和验收契约，领域公理提炼至 domain、理由至 decisions 并互相引用；去掉任务轮次、临时路径与执行调度字段。实际确认来源和必要判断必须在持久文档中可读，不能仅引用被忽略的 intent/progress。
4. settle 只表示需求定稿，未实现/未验证项如实标注。收尾时依据原 acceptance 更新实现与验证状态，记录 reviewed commit、范围和必要证据摘要；规格归位本身不是验收。
5. 更新 `docs/knowledge/specs/index.md` 与知识索引，检查链接和 R 映射。活动任务的 spec 原件与 hash 保留以支持本轮 plan/goal；后续迭代从持久 specs 起步，变更先在任务中审阅，再同步回同一能力。避免两份可独立修改的规格。

语义合并由协调者执行并审阅 diff，不用文件复制冒充合并，不引入自动合并脚本或第二套签署状态。仅定稿归位不修改 plan 的切片状态；完成后再按 [收尾协议](closeout.md) 核对全部产物去向。

## 2. 按需读取与交接

1. 读取 AGENTS/CLAUDE、知识索引和本轮需求，选择相关资料；首次初始化时查现有文档和代码，把与当前任务有关的入口及“何时读取”补入索引。已有 ADR/领域文档只链接，不复制。没有可复用资料可明确记录“暂无”，按本轮实际需求查证。
2. 核对相关链接可读、知识适用范围及当前代码；将猜测与用户裁决区分。发现过期或相互矛盾的知识时，查来源；会影响本轮承诺的冲突进入 intent/spec 裁决，其余知识维护不阻塞需求澄清。
3. 新 plan 的「相关项目知识」记录项目相对路径、适用切片及读取用途。继续已签署旧 plan 时将清单记在 progress，避免为补索引重签历史；新增约束改变范围时仍走增量审阅。
4. goal 编译者将本片相关知识路径及生效约束带入 next-goal；协调者同样写入独立 reviewer 的验收 prompt，要求双方先读。知识是上下文，不能自行扩大已确认的 spec/plan 范围或削弱验收标准。
5. worktree 交接时核对知识文件也在执行区可读，记录相关版本/commit；未提交文件随既有授权的 commit/patch/复制方案交接。不能用另一 checkout 的同名文档代替。执行中知识有变化时检查对当前 goal 的影响，需要改约束则按原绑定协议重新编译。

## 3. 增量维护

默认组织由 `templates/knowledge-index.md` 定义：domain、decisions、conventions、playbooks。目录有实际内容再创建，项目已有合适文档时优先更新原文件。

每次已确认决定改变，更新当前任务正文和受影响引用；长期知识的回写遵守 plan 路径授权。收尾时逐条筛选生效、已验证、可复用内容，合并到知识文件，并在 closeout 记录来源、目标和处置；允许“无新增知识”。

按内容保留必要字段即可，不要求每条知识填整张表：

- 决策：选择、理由、适用边界、用户来源、重估条件；旧决定标注被谁替代，当前索引指向生效版本。
- 领域：跨能力的术语、实体/状态规则、不变量及事实证据；具体需求引用 specs。
- 规范：具体规则、适用范围、例子或验证方法。
- 教训：触发条件、根因、有效处置、验证证据与适用限度。

新增、移动或替代文件时同步索引，逐项核对本次变更涉及的链接、事实和决策一致性。未经验证的推测保留在任务材料，下一轮候选进入 closeout/既有 backlog。原始问答、重试日志和被替代草案留在本地任务目录，清理前将必要持久信息归位。

规格、知识、入口和 `.devloop/.gitignore` 都是可提交的项目文件；仅任务过程材料由该忽略文件排除。setup/init 迁移根 .gitignore 和 Git info/exclude 中可精确识别的旧整目录规则，保留其它规则；仍有宽泛规则遮蔽 specs 时指出命中来源，按实际规则修正。已跟踪过程文件需按明确路径单独处理索引，忽略规则不会自动取消跟踪。

按已授权路径审阅/提交 diff；setup 不暂存、不提交。知识维护不写个人全局 memory，不改变原 acceptance 或将业务验收结论转移到规格/知识提交。
